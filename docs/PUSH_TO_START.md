# Push-to-Start — native Live Activity start for Joba24 (iOS 17.2+)

Status: **implemented, tested, and ready for ONE TestFlight build.**
Global production delivery stays **off**. Only users listed in
`LiveActivityConfig.test_user_ids` can receive anything, and only while
`test_apns` is a literal `true`.

---

## 1. What the user gets

1. A real task event happens (publisher approves a worker, a worker is assigned,
   the worker moves a step).
2. The card **appears on the Lock Screen** with the app closed — no launch, no
   notification tap.
3. It shows the **role-specific and category-specific** wording: the snapshot is
   the same Stage 0 contract the in-app banner renders, so nothing is invented for
   the Lock Screen.
4. The supported action can be tapped **on the card** (see §5 for exactly which).
5. Every later event is an **update to the same card**, never a second one.

## 2. How it works

```
Task event ─► "Live Activity Real Task Dispatch" workflow ─► liveActivityTaskEvent
                                                                │
                            (per recipient: allowlist + test_apns)
                                                                ▼
                                                    dispatchRecipient (shared sender)
                     ┌──────────────────────────────────────────┴───────────────┐
        no committed revision                         a committed revision exists
        + push_to_start + start token                 (or no start token)
                     │                                                 │
                     ▼                                                 ▼
      APNs  aps.event = "start"                       APNs  aps.event = "update" / "end"
      → LiveActivityToken kind="start"                → LiveActivityToken kind="activity"
      → the card APPEARS                              → the card MOVES / CLOSES
```

**The server's `LiveActivityState` row is the memory of "a card already exists for
this (user, task, role)".** It is what makes a start happen exactly once:

* the app's `begin` writes revision 1 *before* it requests its own card → the
  server can no longer start that pair;
* a delivered start commits revision 1 → the app finds a running card and updates
  it (`planActivityStep` matches by task + role), and the server only ever plans
  updates afterwards.

Two independent guarantees, so a duplicate card is not possible even if one of
them is bypassed: the plugin's `start` also ends any existing activity for the
same (task, role) before requesting a new one.

## 3. What was added

| Layer | Change |
| --- | --- |
| `LiveActivityToken` | new `kind`: `activity` \| `start`. Missing = `activity`, so every existing row keeps its meaning. |
| `LiveActivityConfig` | new `push_to_start` switch, default **false**, literal `true` only. |
| `liveActivityAuth.ts` | registration/retirement/eligibility are **kind-aware**. A start-token rotation never retires the activity token of a card that is on screen. |
| `liveActivityPushToStart.ts` | **new** — builds the `start` payload and refuses to build one that could leak a credential. |
| `liveActivitySend.ts` | the remote-start branch, addressed to start tokens only, with the four ANDed conditions. |
| `LiveActivityDispatch` | `event` accepts `start`. |
| `LiveActivityPlugin.swift` | `pushToStartToken` (reads the install token + arms the rotation stream) and `setUserActionAuth` (stores the install-scoped capability). No new Swift file. |
| `JobaActivityAuthStore.swift` | `actionEndpoint()` (https only), the compiled https default, and the install-capability key. |
| `JobaTaskActionIntent.swift` | prefers the card's capability, falls back to the install one, and sends the card's `task_id` + `role`. |
| `liveActivityNative.js` | start-token read/register/rotation, and `ensureUserActionCapability`. |
| `RealTaskActivityBridge.jsx` | one effect: register the token, keep listening, mint the install capability — allowlist only. |

**No new Swift file was added, deliberately.** The Xcode project is generated by
`scripts/patch-ios-live-activity.py`, which registers named files into both
targets; adding a file would mean editing that registry and shipping a build whose
membership nobody verified. Everything new lives in files the patcher already
places in **both** targets (`JobaTaskActivityAttributes.swift`,
`JobaActivityAuthStore.swift`, `JobaTaskActionIntent.swift`) or in the app target
(`LiveActivityPlugin.swift`). The patcher's `--check --require` gate therefore
still proves the whole wiring, and so does `test/liveActivity/stage3.test.js`.

## 4. Security model

**The payload carries no credential.** A start payload holds only what the Lock
Screen may *display*: the frozen snapshot, `attributes { taskId, role }`, and
ordering metadata. `payloadLeaks()` refuses to build a payload containing `token`,
`capability`, `secret`, `user_id`, `email`, `phone`, `endpoint` or a session — and
the tests pin that.

**The start token is not a capability.** It is an opaque Apple value that can only
make a card appear for this app; it cannot read anything. It is registered by the
signed-in user, for themselves only (`registerLiveActivityToken` re-derives the
recipient from the session).

**The button on a remotely started card** cannot use the per-card capability,
because no session existed while the app was closed. The bounded answer is an
**install-scoped capability**:

* one user, **no task**, only the two action ids a card can offer;
* **12 hours**, refreshed on every app launch (the per-card one is sized to the
  task and can live up to a week);
* every tap must also carry the card's `task_id` + `role`, and the endpoint
  re-reads the record and re-derives ownership (`authorizeActivity`) before doing
  anything;
* it is stored only in the App Group, never in a payload, a URL, a log or the
  content state;
* it is minted **only for allowlisted testers** — the same gate as the start push.

Residual risk, stated plainly: for up to 12 hours the App Group holds a value that
lets our own action endpoint attempt an action as this user, on **their own** task,
and only for the two action ids. It grants no reads and no other operation. It is
wider than a per-card capability, which is why it is time-boxed and allowlist-only.

## 5. Which actions work from the Lock Screen, and which need the app

| Action | From the card? | Why |
| --- | --- | --- |
| Worker: next step (set out / arrived / finish) | **Yes**, one tap | One `worker_status` write, re-authorized from the record, exactly what the in-app button does. |
| Publisher: approve completion | **Yes**, two taps (confirm, then submit) | Runs `completeTask` itself — counters, refunds, ledger, idempotency. Irreversible, so the first tap only asks. |
| Applicant list, choose/reject a candidate | **No** | A fixed small card cannot hold a list; it opens the task. |
| Chat, phone, navigation | **No** | Needs a keyboard / another app. |
| Invoice, proof upload, reschedule | **No** | Needs the camera, files, or a calendar. |

The card always offers **one** action — the one this role may take right now,
worded by the server from the category's own flow. Nothing is hidden: when there is
no legal action, the card simply carries none.

## 6. Audit — is the `capacitor://localhost` → https fix in the installed intent?

**Answer: the endpoint is not compiled into Swift at all, so the fix does reach an
already installed iPhone — but only after the app is opened once, and only because
the endpoint lives in the App Group.**

Evidence:

* `JobaTaskActionIntent.swift` reads `JobaActivityAuthStore.endpoint()`; no URL
  literal was compiled in (verified: no `capacitor://` anywhere in `ios/`).
* The bad value came from **JavaScript** (`window.location.origin` inside the
  WebView = `capacitor://localhost`) and was written into the App Group by
  `setActionAuth`.
* The current JS fix overwrites that stored value with an https endpoint on the
  next session (`ensureActionCapability` on every start/update pass).

Therefore: **no new build is required for the endpoint fix**, provided the app has
been opened since the fix shipped. This build additionally makes the endpoint
unconditionally https — the store now refuses to persist a scheme URL, and the
intent falls back to a compiled `https://joba24.com/functions/liveActivityAction`
when the stored value is missing or not https. Everything else in this change
(start tokens, the install capability, the intent's fallback) **is** compiled and
**does** require the new TestFlight build.

## 8. Operator setup (once, before the two-device test)

1. Apple Developer → the App ID → enable **Push Notifications** and **Live
   Activities**; the widget extension already carries the matching entitlements.
2. Secrets are already present: `APNS_KEY_ID`, `APNS_TEAM_ID`,
   `APNS_PRIVATE_KEY`, `APNS_BUNDLE_ID`, `LIVE_ACTIVITY_ACTION_SECRET`.
3. `LiveActivityConfig` (single row):
   * `test_user_ids`: the **two** tester user ids;
   * `test_apns`: `true`;
   * `environment`: **`production`** for a TestFlight build;
   * `push_to_start`: `true` (only for this test);
   * `enabled`: leave **`false`** — it is not needed for allowlisted testers and
     keeps every other user untouched;
   * `dry_run`: leave **`true`**.
4. If APNs rejects the start with an attributes-type problem, set the non-secret
   `APNS_ACTIVITY_ATTRIBUTES_TYPE` to `JobaActivityWidget.JobaTaskActivity` and
   retry. The default is Apple's documented plain type name.
5. Install the new TestFlight build on **both** phones and open the app once while
   each tester is signed in (this is what registers the start token and the
   install capability).

## 9. Two-device test plan

Devices: **A = publisher**, **B = worker**. Both signed in as allowlisted users,
both with the new build, app **force-closed** (swipe up in the app switcher) unless a
step says otherwise.

**T1 — Tokens are registered (device by device)**
Open the app once on A, then once on B. Then confirm that each user now has exactly
one `LiveActivityToken` row with `kind: start` (activity tokens appear later, once a
card exists). Expected: one `start` row per device, `environment: production`,
`status: active`.

**T2 — Remote start, publisher side (the main test)**
Force-close A. From B (or admin) publish a task priced above the threshold, then
approve B as the worker **while A's phone is locked**. Expected on A: the card
appears within ~10 s, shows the publisher wording for the current step, and no
second card appears. Record: `LiveActivityDispatch` row with `event: start`,
`status: sent`, `apns_status: 200`, and `LiveActivityState` revision 1.

**T3 — Remote start, worker side**
Force-close B. From A, approve B. Expected on B: card appears, worker wording, with
the next-step button.

**T4 — No duplicate card when both start**
Force-close A. Approve B, then **open A immediately** (within a few seconds).
Expected: A's card is updated, not replaced — one card only, and no `start` dispatch
after the first. Then repeat with A open *first*: the app starts the card, and the
server must send **no** `start` (its state row already exists).

**T5 — Interactive action on a remotely started card**
On A's card (started in T2, app still closed): the publisher action is hidden until
the worker reports done. On B's card (T3): tap the next step. Expected: the card
moves to the next step within a few seconds, `LiveActivityState` revision advances,
and a `LiveActivityDeviceEvent` (`action_applied`) is recorded once B next opens the
app. If it shows a failure glyph, the stage recorded in the App Group names the
reason (`no_capability`, `http_409:…`, `network_error`).

**T6 — Remote start for a device that has never opened this build**
Uninstall and reinstall on A, sign in, then force-close. Approve B. Expected: the
card may not appear (no start token registered yet) — this is the documented limit.
Open A once, repeat: it appears.

**T7 — Update, not recreate**
With a card on B's screen, have A change the task (edit the price, or advance a
step). Expected: the same card updates in place — `activityId` unchanged in
`LiveActivityDeviceEvent`, `event: updated`, revisions increasing.

**T8 — End**
Complete the task from the app. Expected on both phones: the card closes
immediately, `LiveActivityDispatch` has `event: end`, and no further update arrives
for that task.

**T9 — Rotation and multiple devices**
Reset A's install (delete and reinstall, same Apple ID). Open once. Expected: a new
`start` token row, the old one `status: invalid`, `invalidated_reason:
superseded_by_new_token`, and **no** retirement of any activity token. Sign the same
user in on a second iPhone and repeat T2: **both** devices show the card.

**T10 — Unsupported iOS fallback**
On an iOS 16.x device (any account not on the allowlist behaves the same way):
`pushToStartToken` returns `supported: false`, no start row is written, and the app
still starts the card itself when it is open — the previous behaviour, unchanged.

**T11 — The endpoint is https**
On a device that ran the *old* build, open the app once, then tap the card's action.
Expected: `applied` (not `network_error`). This proves the stored endpoint was
overwritten by the JS fix.

**T12 — Production stays closed**
With `push_to_start: true` and `test_user_ids` holding only A and B, sign in as a
third, non-allowlisted user and repeat T2/T3. Expected: no card, no dispatch row,
`skipped: no_tracked_recipients`.

## 10. Known limits

* **iOS 17.2+** for remote start. Older versions keep the local-start fallback.
* A device that has never run this build has no start token, so it cannot be
  started remotely until the app is opened once (T6).
* A start push shows a card, not a banner: no sound, no alert. The app's own
  notification path is unchanged and not duplicated.
* `attributes-type` uses Apple's documented plain type name; the non-secret
  `APNS_ACTIVITY_ATTRIBUTES_TYPE` escape hatch exists if a given Xcode/OS build
  wants the module-qualified form.
* One card at a time on a device: the bridge still tracks the single active task,
  exactly as the banner does.
